# W2-A - cache construction boundary, and the module boundary it protects

W2-A is the cache construction boundary only. It deliberately does **not** create a
MemoryTrustRepository, because an instance that no real path goes through is dead
wiring: it would make the source look composed without closing Gate B.

What W2-A establishes, and what it explicitly does not:

    process cache owner              ESTABLISHED   ProbeApplication.memoryCache (by lazy)
    Room hidden behind cache module  ESTABLISHED   RoomMemoryCache.open() returns MemoryCache
    test cache isolation             VERIFIED      per-subject clearSubject before launch

    Activity repository owner        NOT YET       this is W2-B
    Gate B runtime enforcement       NOT YET       this is W2-B

## The boundary, read off the dependency graph rather than asserted

`:app:dependencies --configuration debugCompileClasspath`, filtered:

    androidx.room matches on :app debugCompileClasspath = 0
    +--- project :core-memory-cache-android

`:app` reaches the cache module and never sees Room, the DAO or MemoryCacheDatabase.
Room stays an `implementation` dependency of `:core-memory-cache-android`, and the
constructor is `internal` so this module's own androidTest can still build one over an
in-memory database while `:app` cannot.

This is the property the previous W2 plan would have broken: calling
Room.databaseBuilder from ProbeApplication would have forced a second, product-layer
Room dependency and leaked the persistence choice up out of the module that owns it.

## Test isolation

Each method runs in its own process but all share one deviceId and one on-disk
database, and the fixtures reuse ids (m1, s1, r1). Once the screen reads through a
cache, a previous method's rows are still there - and because the repository emits the
cached frame *before* the refresh, a test could observe another test's memory under the
same id. The cache surviving a restart is correct; the fixture has to be explicit about
starting clean.

launchWithGateway() therefore resolves the subject, calls the production
clearSubject(subjectId) partition API, installs the gateway, and launches. Two tests
deliberately do not use it:

    withoutAGatewayTheScreenSaysSoAndInventsNothing
        has no gateway at all, so it must reach the screen without one
    aDamagedIdentityMakesTheSurfaceUnavailableWithoutInventingASubject
        reading the identity to find the subject would warm the store, and that test's
        whole point is a process that has not yet read a corrupted file

No test-only cache seam was added, and deleteDatabase()/clearAllTables() were not used:
clearSubject already exists and is already the production partition API.
